# `code` command + cd-guard scoped to managed workspaces

## Goal
1. New `code` shell command: no-args → fzf picker of the current repo's jj
   workspaces, selection focuses (or creates) the matching herdr workspace;
   `code <name>` → focus existing or create new.
2. cd-guard becomes strictly opt-in per managed workspace: it only activates in
   herdr workspaces opened via `code` / `wt switch` (i.e. by `herdr-ws-open`).
   No manual `guard on` elsewhere.

## Design

### 1. Guard enablement model (state-driven)
`~/.config/herdr/plugins/config/aamini.cd-guard/roots` (`<workspace_id>\t<root>`)
becomes the registry of *managed* workspaces, written/removed by herdr-ws:
- `herdr-ws-open` **arms**: after create/focus it knows the herdr workspace id
  (create response / `find_workspace`) and the path → upsert into `roots`.
  While arming, prune entries whose ids are no longer live (it already fetched
  the workspace list) so stale session ids don't accumulate.
- `herdr-ws-close` **disarms**: after closing, remove the id from `roots` and
  `disabled`.
- Arming is best-effort: failure logs to stderr but doesn't fail the open.

### 2. `.zshrc` guard section changes
- New `_herdr_guard_managed`: true iff `roots` has an entry for
  `$HERDR_WORKSPACE_ID`.
- `_herdr_guard_chpwd`: return early unless managed (before the disabled check).
- `guard on`: only re-enables per-shell (`unset HERDR_GUARD_DISABLED`) when
  managed; otherwise prints `cd guard: only active in code/wt workspaces` and
  does nothing. `guard off` unchanged (per-shell). `guard status` prints
  `unmanaged` when no entry.
- Root resolution unchanged (`roots` entry → `$HERDR_GUARD_ROOT` fallback is now
  unreachable in practice since managed implies an entry; keep as safety).

### 3. `code` command (`.zshrc`, near the djo section)
```zsh
code() {
  # requires jj repo + herdr
  local primary=$(jj root) || return
  # args: code <name> → existing? herdr-ws-open <path> --project-path primary
  #                  → new?      wt switch -c <name>   (hook opens herdr ws)
  # no args → djo list --json | names (minus `default`) | fzf
  #           → herdr-ws-open <path> --project-path primary  (no shell cd)
}
```
- Picker source: `djo list --json` (verify field names at impl; `--full` adds
  path if plain `--json` lacks it). Exclude `default` (the primary checkout —
  its herdr label `ws-<repo>-default` wouldn't match the user's existing main
  herdr workspace).
- Existing-name path calls `herdr-ws-open` directly: focuses or creates the
  herdr workspace without cd'ing the current shell. New-name path goes through
  `wt switch -c` (jj workspace must be created; its post-switch hook opens the
  herdr workspace; shell cd is acceptable there).
- Guards: not in a jj repo → error; `HERDR_ENV` unset → error (focusing is the
  point; dojjo hooks would fail anyway).

### 4. Plugin script touch-up
- `tools/herdr-cd-guard/status.sh`: report `unmanaged` when no `roots` entry.
  toggle.sh / set-root.sh unchanged (`disabled` semantics intact; set-root
  effectively arms, which is reasonable).

## Interactions
- Manual pane splits inside a managed herdr workspace: new shell sees the
  `roots` entry → guarded. Correct.
- Plain herdr workspaces (agent panes, `ui`): no entry → no guard. Correct.
- herdr restart → new ids; entries re-armed on next `code`/`wt switch`; stale
  ids pruned at arm time.
- `herdr-ws-open` is called by dojjo hooks from any cwd — arm must not depend
  on `$HERDR_WORKSPACE_ID` of the caller (it uses the id of the opened
  workspace).

## Verification
1. `mise run //tools/herdr-ws:check` (lint, format, 18+ unit tests).
2. Pure-zsh: no `roots` entry → `cd /` allowed; add fake id entry → blocked;
   `guard on` without entry → refusal message.
3. Live: `code close-test2` (new name) → jj workspace + herdr workspace appear,
   pane there is guarded (`cd ~` blocked); plain workspace pane (`cd ~`) stays
   unguarded; `wt remove close-test2` → herdr workspace closed + `roots` entry
   gone. `code` no-args picker checked manually by user (fzf interactive).
